## Issues discovered
- **`fake_cloud_firestore` transaction merge bug (confirmed empirically, documented in code
  comments on `firestore_service.dart` and `firestore_profile_repository.dart`):** within one
  `runTransaction` call, a *second* `tx.set(sameDoc, {...}, SetOptions(merge: true))` call to
  the **same** document reference does not merge against an *earlier* `tx.set` to that same
  document within the same transaction — it silently replaces the document with only its own
  keys. Every prior task's `seedWriter` only ever wrote to a `users/{uid}` *subcollection*
  document (different doc reference from `userDoc` itself), so this never surfaced. F18 is the
  first seedWriter whose data belongs directly on `userDoc` — the same document
  `runBootstrapIfNeeded`'s own trailing `seeded: true` commit touches — so it collided
  immediately. Fixed by adding an additive `extraFields` parameter to `runBootstrapIfNeeded`
  that gets merged into the **one** existing final `tx.set` call, rather than writing a second,
  separate `tx.set` to the same document. Verified this is additive: ran the existing
  `firestore_service_test.dart` suite unmodified (14/14 still pass) and confirmed a blanket
  `tx.update()` alternative (considered and rejected) would have broken F14-A15-style tests
  where no seedWriter ever creates `userDoc` at all. **Flag for whoever lands Task 6 (wishlist)
  or any later task whose seed data also belongs on the top-level `users/{uid}` document
  itself (not a subcollection): use `extraFields`, not a second `tx.set` inside your own
  `seedWriter`, or you will hit the same silent data loss in tests (and very possibly in real
  Firestore too — I did not get to verify real-Firestore semantics for this specific case,
  since the project policy is fake-double-only for unit tests; flagged as unverified for A20's
  live pass).**
- **`runBootstrapIfNeeded` has no production call site anywhere before this task.** Searched
  `lib/` prior to this task's changes: `FirestoreWardrobeRepository`, `FirestoreOutfitsRepository`,
  and `FirestorePlannerRepository` all have the mechanism unit-tested (F14/F15/F16/F17 test
  files) but `lib/app.dart` never actually calls `FirestoreService.runBootstrapIfNeeded` for
  any of them — a brand-new signed-in user today gets **no** wardrobe/outfits/planner seed
  data at all in the running app, only in tests. This task's `lib/app.dart` change is the
  **first** production call site for `runBootstrapIfNeeded`, and it only seeds the `users/{uid}`
  document's own profile fields + `wishlist: []` — it does **not** retroactively wire
  wardrobe/outfits/planner subcollection seeding into `app.dart` (out of scope for this task;
  would have widened scope beyond the Profile repository/cubit/app.dart files named in the
  brief). **Flagged for the plan owner:** if D5's "brand-new user gets seeded sample data" is
  still an intended behavior, a follow-up task needs to wire the other three repositories'
  bootstrap calls into `app.dart` too — today only Profile's own fields get seeded.
- `BlocProvider`'s `create` callback is lazy by default — a test that checks a Firestore side
  effect of construction (the bootstrap write) without first triggering a `context.read`/
  `context.watch` on that Cubit will see nothing happen. Cost one fix round while writing
  `F18_A16_app` in `app_backend_wiring_test.dart` (added an explicit `read<ProfileCubit>()`
  before polling). Noting this for later tasks' own app-level tests.
- `ProfileState` has no `==`/`copyWith`-aware equality override — tests must compare individual
  fields rather than whole-object `expect(state, const ProfileState())`, since two
  non-canonicalized instances with identical field values are not `identical`/`==` to each
  other. Not a bug, just a gotcha that cost one local fix in
  `profile_cubit_dual_mode_test.dart`.
