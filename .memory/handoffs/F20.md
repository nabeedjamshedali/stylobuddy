# Handoff — F20 Packing Backend (Trip Persistence)

## Completed
- `lib/features/packing/repository/packing_repository.dart` — abstract `PackingRepository`
  interface per the Task 7 controller ruling: ONE `saveTrip(Trip trip, {required bool
  isNew})` create-or-update method, FIVE separately-named items-mutating methods
  (`toggle`, `removeItem`, `addWardrobe`, `addCustom`, `generateChecklist`), plus
  `watchTrips()`/`deleteTrip()`.
- `lib/features/packing/repository/in_memory_packing_repository.dart` — guest-mode
  repository, today's exact `PackingCubit` trip-list logic moved behind the interface
  verbatim; every write returns `SynchronousFuture`; a shared private `_mutateItems`
  helper backs the five items-mutating methods; zero Firestore import (F20-A13).
- `lib/features/packing/repository/firestore_packing_repository.dart` — signed-in
  repository. `saveTrip`'s create branch does a typed whole-document `set()`; its edit
  branch is a targeted raw-map merge-set that NEVER includes the `items` key (so it can
  never clobber a concurrently in-flight items mutation). The five items-mutating
  methods share a private `_mutateItems` helper built on `runTransaction`, reading the
  trip fresh from the server and writing the whole `Trip` back with only `items`
  changed. A missing target document is a silent no-op (A15). `watchTrips()` defaults a
  missing `items` field to `[]` and sorts newest-first by doc id to match guest-mode
  ordering.
- `lib/features/packing/cubit/packing_cubit.dart` — rewritten to the dual-mode factory
  pattern (`PackingCubit({PackingRepository? repository})`, defaulting to
  `InMemoryPackingRepository()`), subscribing to `watchTrips()` with an `onError`
  handler (A18), and optimistic-update-then-reconcile for `saveDraft`,
  `generateChecklist`, `toggle`, `removeItem`, `addWardrobe`, `addCustom`, and
  `deleteSelectedTrip` — each applies its existing synchronous optimistic emit exactly
  as before, then fires the matching repository call unawaited with a `catchError`
  that reverts ONLY the one trip's one changed aspect, evaluated against the Cubit's
  CURRENT state at failure time (never a captured-before-the-call whole-list/whole-trip
  snapshot). `suggestions()` is untouched.
- `lib/app.dart` — `PackingCubit` is now constructed with `InMemoryPackingRepository()`
  for `uid == null` and `FirestorePackingRepository(FirestoreService(...), uid)` for a
  signed-in uid, following the same pattern as F15-F19's own dual-mode wiring. No other
  change to `app.dart`.
- Tests added (all new, zero pre-existing file touched):

    A01, A02, A03, A05, A06, A07, A08 (+ a non-clobber structural variant), A15, A16,
    A19.
  - `test/features/packing/in_memory_packing_repository_test.dart` — 3 tests covering

  - `test/features/packing/packing_cubit_dual_mode_test.dart` — 6 tests covering

  - `test/app_backend_wiring_test.dart` — appended `F20_A11` (app.dart-level dual-mode
    test through a real `StyloBuddyApp`/`uidStream`/`firestoreOverride` harness with

## Issues discovered
- **Controller ruling vs. feature doc §6/§13 conflict (expected, resolved per the
  brief):** the feature doc's own §6/§13 specify a single `createTrip`/
  `updateTripDetails` split plus one generic `mutateItems(tripId, transform)` method.
  The task-7 brief's binding controller ruling instead requires ONE `saveTrip`
  create-or-update method and FIVE separately-named items-mutating methods. Implemented
  per the brief (binding) — documented explicitly in the feature doc's completion
  block per the implementer contract ("if the two conflict, the feature document wins
  — note it in your report" — here the brief itself states it resolves the doc's own
  §13 open questions, so the brief's ruling was followed, and the conflict is recorded
  rather than silently overridden).
- `InMemoryPackingRepository.watchTrips()` is single-subscription (mirrors
  `InMemoryOutfitsRepository`/`InMemoryWardrobeRepository`'s own documented stance) —
  a test that needs two `PackingCubit`s to observe the SAME in-memory repository
  instance will throw "Stream has already been listened to". Worked around in
  `packing_cubit_dual_mode_test.dart`'s A09/A10 tests by using a single Cubit/repository
  instance with a mutable `failing` set armed only after fixture data is already
  written, rather than constructing a second Cubit against the same repository.
- No new field, type, or `firestore-schema.md`/`03-domain-model.md` change was needed —
  confirmed per the feature doc's own §13 final note.
