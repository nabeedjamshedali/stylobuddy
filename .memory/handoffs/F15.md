## Issues discovered
- **Stream delivery is never synchronous in Dart — real regression caught before it shipped.**
  Routing `WardrobeCubit`'s initial state purely through `repository.watchItems()`'s first event
  (as architecture D6 literally describes) broke 2 of F14's own guest-mode widget tests
  (`F14_A07`, `F14_A08`) — a guest's wardrobe would render **zero items for one frame** before the
  seed data arrived (confirmed with a throwaway debug print: the emit happened *after* the test's
  assertion, inside `pumpAndSettle`'s teardown window, not within it). `pumpAndSettle`'s heuristic
  ("no more frames scheduled") can return before a microtask-delivered Stream event that itself
  would schedule the *next* frame. Fixed by giving `InMemoryWardrobeRepository` a synchronous
  `snapshot` getter that `WardrobeCubit`'s constructor consults directly (via an `is
  InMemoryWardrobeRepository` check) for its initial `WardrobeState`, bypassing the Stream for
  that one value only. `FirestoreWardrobeRepository` has no such synchronous value — it legitimately
  starts empty until its first snapshot, which is new, expected behavior for that mode. Documented
  in both files' doc comments.
- **Architecture D6's "await the write, then optimistically update" is incompatible with
  guest-mode's synchronous test suite.** `await`ing *any* Future (even an already-resolved one)
  always defers continuation to a microtask in Dart — doing that before `emit()` would have broken
  every F06 test that calls a `WardrobeCubit` write method and asserts on `state` synchronously in
  the same statement block (no intervening `await`). Resolved by keeping every write method
  synchronous/void: the optimistic local update applies immediately (today's exact behavior), and
  the repository's own persistence call fires in the background (`unawaited`). For a signed-in
  user the later Firestore snapshot still reconciles the same data. Flagging since this is a
  deliberate, reasoned deviation from the architecture doc's literal wording, chosen because F15's
  own "zero existing assertion edited" requirement is the higher-priority binding rule when the two
  are in tension.
- **`FirestoreService()`'s default constructor isn't resilient to "Firebase not initialized" — this
  broke F14's own widget-test suite once a real per-feature repository construction landed.**
  `app.dart`'s `uid-1` fake-sign-in tests (`test/app_backend_wiring_test.dart`) never call
  `Firebase.initializeApp()` by design (that's the whole point of the `uidStream` test seam); once
  `FirestoreWardrobeRepository(FirestoreService(), uid)` is actually constructed for that fake
  `uid-1`, `FirebaseFirestore.instance` throws synchronously. Fixed by adding a `firestoreOverride`
  test-only constructor param to `StyloBuddyApp` (same established pattern as `router`/`uidStream`/
  `initialUid`) and updating `test/app_backend_wiring_test.dart` to pass a `FakeFirebaseFirestore()`
  at every construction site. This is a necessary, minimal fix — without it, F15-A09's own
  assertion (dual-mode construction differs by uid) would be untestable via the existing harness —
  but it does touch a test file one layer outside this task's named file list, flagged per the
  contract's instruction to report file-list deviations.
- **Supabase JWKS endpoint path is singular (`/jwk/`), not plural (`/jwks/`).** The plural form
  404s against the real Google endpoint — caught live while verifying F15-A25, not by the local
  unit tests (which use a local JWKS double and never hit the real URL). Fixed in
  `firebase-auth.ts`; the doc comment records the discovery so it isn't silently "obvious" to the
  next reader.
- **Supabase's gateway-level JWT verification must be disabled for `storage-upload-url`.** By
  default every deployed Edge Function requires its `Authorization` header to be a valid *Supabase*
  JWT; a Firebase ID token in that header is rejected (`UNAUTHORIZED_ASYMMETRIC_JWT`) before this
  function's own code ever runs. Fixed via `supabase/config.toml`'s `verify_jwt = false` for this
  function (and the `--no-verify-jwt` deploy flag, now redundant with the config but used during
  the fix). This is load-bearing — every future deploy of this function must preserve it.
- **This project's `SUPABASE_SERVICE_ROLE_KEY` secret is the new `sb_secret_...` key format, not a
  legacy JWT**, and the raw Storage REST endpoint (`/object/upload/sign/...`) rejects it
  ("Invalid Compact JWS") when sent as a bare `Authorization: Bearer` header. Switched
  `createSignedUploadUrl` from a hand-rolled REST call to the official `@supabase/supabase-js`
  client, which handles this correctly. Side effect: the client's `createSignedUploadUrl` does
  **not** support a caller-supplied expiry for *upload* URLs (only `createSignedUrl`, for
  downloads, does) — the storage spec's "60-second expiry" requirement is not achievable via the
  current Supabase API for upload URLs; the live-verified token had a 2-hour expiry instead. This
  is a real constraint of Supabase's current API, not an oversight — documented in
  `index.ts`'s doc comment and flagged here for whoever owns the storage spec doc.
- **`user-photos` is a private bucket**, so the "public object URL" shape `StorageRepository`
  constructs 400s if actually fetched today. Harmless for this task (nothing reads it back into a
  widget yet) but flagged clearly — see Not completed.

## Fix round (review findings, 2026-10-20)

A review found 4 Important issues, 3 assertions without genuine tests, and 7 Minor nits. All 4
Important issues fixed; all 3 missing-test gaps closed; 6 of 7 Minor nits fixed, 1 left as a
documented structural decision (see below).

### Important fixes
1. **Fire-and-forget writes had no error handling (would surface as FATAL Crashlytics reports).**
   `WardrobeCubit`'s `addItems`/`updateItem`/`removeItem`/`adjustWears` each now attach
   `.catchError` to their `unawaited(...)` repository call (logs via `debugPrint` in debug mode,
   never rethrows); the `watchItems().listen(...)` subscription now has an `onError` callback
   (logs, keeps last known state, subscription stays alive for the next successful snapshot).
   Tests: `test/features/wardrobe/wardrobe_cubit_error_handling_test.dart` (3 new tests, using
   `runZonedGuarded` to prove no unhandled async error surfaces).
2. **`FirestoreWardrobeRepository.adjustWears` was a non-transactional read-modify-write, racing
   under concurrent calls (`OutfitsCubit`'s log-wear/undo-wear).** Rewritten using
   `FirebaseFirestore.runTransaction`, reading every id before writing any of them (Firestore
   requires all transaction reads before any write — this also fixed a latent bug in the existing
   `F15_edge` "skips a missing id" test, which started throwing once a transaction was introduced
   with a naive interleaved get/set loop). Discovered live: `fake_cloud_firestore` has no
   optimistic-concurrency/retry-on-conflict model, so a test that fires two genuinely concurrent
   `adjustWears` calls against it cannot distinguish "fixed" from "still racy" (confirmed: such a
   test flaked regardless of the production code). Replaced the originally-planned true-concurrency
   test with (a) a reads-before-writes-across-multiple-ids correctness test and (b) a structural
   source check that `adjustWears` uses `runTransaction` (not a plain batch), per the review's own
   documented fallback instruction.
3. **Upload HTTP calls (`storage_repository.dart`) had no timeout, violating A12.** Added a
   30-second default timeout (`.timeout(...)`) to both the signed-URL `POST` and the file `PUT`,
   via a new injectable `networkTimeout` constructor parameter (defaults to 30s in production; a
   test overrides it to 200ms so the "bounded, not hanging" guarantee can be proven without waiting
   out the real 30 seconds). Test: `F15_important3` in `test/shared/backend/storage_repository_test.dart`.
4. **`ImportCubit.confirmCurrent` was re-entrant across the upload `await`, so a double-tap could
   duplicate the save.** Added a `saving: bool` to `ImportState`; `confirmCurrent` no-ops (returns
   `null`) if already in flight, guarded by try/finally so `saving` always resets even on an
   exception. Test: `F15_important4` in `test/features/wardrobe/import_cubit_test.dart` (fires two
   `confirmCurrent` calls before the first's upload `Future` resolves, via a `Completer`, asserts
   only one `uploadWardrobePhoto` call and one saved item).
