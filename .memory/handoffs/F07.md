# Handoff — F07 Manual Outfit Builder

## Completed
- Routes `/builder /manual-preview` wired in `lib/features/builder/builder_routes.dart` (replaced the
  `GenericPreviewView` placeholder), matching the prototype (`app.js:158-169`, `styles.css:347-349`) screen for
  screen: copy, layout order, categories, and navigation.
- `BuilderCubit` (`lib/features/builder/cubit/builder_cubit.dart` + `builder_state.dart`), provided at the app
  root in `lib/app.dart` next to the other root cubits (same precedent as `StylistCubit`/`WardrobeBrowseCubit`).
  Public surface, exactly as the contract specifies:
  `BuilderState{List<String> picked; String category; int? editingId; String name; String occasion}` with
  `bool get isEditing`, and `BuilderCubit{void start({int? editId}); void setCategory(String); void
  setName(String); void setOccasion(String); void toggle(String id); void remove(String id);
  BuilderSaveResult save();}`.
  - `start(editId)` seeds `picked`/`name`/`occasion` from `OutfitsCubit.byId(editId)` when it exists; `editingId`
    is always set to the given `editId` even when the lookup misses (mirrors the prototype's
    `S.manualEditing=editId` which is set unconditionally), so a stale id still reaches `save()`, which falls
    through to `OutfitsCubit.upsertManual`'s own not-found branch and creates a fresh outfit instead of throwing
    (F07-A08).
  - `save()` returns `BuilderSaveResult{String message; int? outfitId}` (`lib/features/builder/models/
    builder_save_result.dart`) instead of touching `BuildContext` directly — the view shows the toast and
    navigates based on the result. Validates name-then-items (blank name wins per F07-A04), trims the name,
    calls `OutfitsCubit.upsertManual`, then resets `picked`/`editingId`/`name` (not `category`/`occasion` —
    matches the prototype's `manualSave()`, which also leaves those two alone).
- Views: `lib/features/builder/view/builder_view.dart`, `manual_preview_view.dart`.
- Widgets under `lib/features/builder/widgets/`: `mb_intro.dart` (shared kicker/title/body block),
  `mb_live_preview.dart` (live composition grid, capped at 6 with remove buttons, plus the full tag row and the

  `mb_summary_row.dart`, `mb_form.dart` (name field + "Best for" select).
- `lib/features/builder/builder_tokens.dart`: all `.mb-*` CSS values (V13).
- Navigation: `builder → manual-preview` via `context.push`; manual-preview's "Change Items" and the per-piece
  "Change" buttons go back via `context.push(AppRoutes.builder)` (prototype precedent: the sibling matching
  feature's "Edit selected items" also re-pushes rather than popping); a successful save does
  `context.go(AppRoutes.savedDetail(id))` (flow completion, per the dispatch ruling, not a drill-down). Header
  back targets: builder → `/wardrobe` fallback, manual-preview → `/builder` fallback (both via the shared
  `ScreenHead` pop-or-fallback behavior).
- Wardrobe's "Build outfit" button (`lib/features/wardrobe/view/wardrobe_view.dart`) now calls
  `BuilderCubit.start()` before pushing `/builder`, so every fresh "Create a look" entry resets the draft
  (picked/name/occasion/category) — this was a one-line addition outside `lib/features/builder/`, flagging per
  instructions. `BuilderCubit`'s own default constructor state is already the fresh-draft shape, so navigating
  straight to `/builder` without calling `start()` first (e.g. deep link, or before any other feature wires its
  own "Create a look" button) still renders correctly the first time.
- The manual-preview name field keeps its cubit state in sync on every keystroke (`TextEditingController`
  listener calling `BuilderCubit.setName`) rather than only committing on Save/Change Items like the raw HTML
  input — functionally equivalent for every assertion, simpler to test, and avoids stale state if the user
  navigates away some other way. The default-name prefill ('My custom look') is written back to the cubit via
  `addPostFrameCallback` in `initState` so it behaves as a *real* value (clearing it is then rejected on save,
  matching §12's edge case), not just a placeholder hint.
- Occasion options on manual-preview are the prototype's own literal list — `['Everyday','Office','Casual',
  'Party','Wedding','Date Night','Vacation']` — defined locally in `_ManualPreviewViewState`, **not**
  `SeedData.occasions` (different order and content: SeedData has `Travel`, the prototype has `Vacation`). This
  is a likely prototype content inconsistency; flagging for the parity pass in case it should be unified.

## Issues discovered
- `BuilderView`'s "Choose from your wardrobe … N pieces" row overflowed `RenderFlex` at 390px width with a plain
  `Row` (unlike other screens' similarly-worded headers, this exact string plus the DM Sans bold weight didn't
  fit); fixed by wrapping the label in `Expanded` + `TextOverflow.ellipsis`. No functional change, just a layout
  fix caught by the widget tests.
- `AppToast`'s static timer means every test that triggers a toast must `await drainToast(tester)` before the
  test ends (existing convention from other features' handoffs) — applied in `test_F07_A17_...`; `save()`
  always returns a message, but only toast-showing tests needed the drain (navigation-only paths like Change
  Items don't toast).
- `BuilderCubit` doesn't depend on `WardrobeCubit` at all — only `OutfitsCubit` (for `byId`/`upsertManual`).
  Wardrobe item lookups (`itemOrFallback`) happen directly in the grid/preview widgets via
  `context.watch<WardrobeCubit>()`, the same pattern as `MmItemsGrid`/`ItemTileGrid`. The brief's "Consumes:
  ... WardrobeCubit" refers to the feature as a whole, not the cubit's constructor.
