## Issues discovered
- The shared `AppProgressBar` widget (`lib/shared/widgets/progress_bar.dart`) hardcodes `AppColors.green` (`#086B52`) as its fill color, but the V16 CSS's `.pk-trip-progress`/`.pk-progress` fill is `#087F62`, a different (close but not identical) green. Packing could not reuse it without an exact-color regression, so it got its own `PkProgressBar` in `packing_tokens.dart`/`widgets/pk_progress_bar.dart`. Worth flagging to whoever owns `lib/shared`: either `AppProgressBar` should take a color parameter, or multiple near-identical progress-bar widgets will keep appearing across features.
- Similarly, the shared `SelectField` and the `.pk-form` select use slightly different border colors (`SharedTokens.fieldBorder` `#E4E9E5` vs this feature's `#DFE7E2`), so a feature-local `PkSelectField` was written instead of reusing the shared one. Same applies to the "field box" look for date/text inputs. This is consistent with the global-constraints rule ("feature-only CSS values go in `<feature>_tokens.dart`") but means the shared widgets are mostly not reusable as-is for packing.
- `WardrobeCubit.itemOrFallback` is used (read-only) for resolving `imageId` wherever a `PackingItem.wardrobeId` is shown (preview grid, checklist, add grid); confirmed it already degrades gracefully for removed ids (F10-A25), no change needed there.
- The prototype's `.pk-button` label and trailing `→` are two separate DOM nodes placed by `justify-content: space-between`; `PkPrimaryButton` renders them as two `Text` widgets in a `Row` (not concatenated into one string) to get the correct spread-across-the-button-width layout. Tests therefore match on the label text alone (e.g. `tapText(tester, 'Continue to packing plan')`), not the label+arrow string. Noting this since other features' primary buttons (`CalendarPrimaryButton`) concatenate `'$label →'` into one `Text` — that pattern is only correct when the CSS **doesn't** space-justify, so it shouldn't be copied blindly for pk-button-style layouts.
