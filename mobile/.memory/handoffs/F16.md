## Review-fix round (2026-10-20)
- `InMemoryOutfitsRepository`'s write methods now return
  `SynchronousFuture(...)` (not `async`) — guest-mode writes resolve
  inline, so `logWear`/`removeWear`'s now-deferred
  `WardrobeCubit.adjustWears` call (required for guest mode too, since
  the Cubit doesn't branch by repository type) incurs zero added latency.
  This made the microtask-flush edits to `outfits_cubit_test.dart` and
  `saved_screens_test.dart` (described in the superseded bullets above)
  unnecessary; both files — and `builder_cubit_test.dart`'s unrelated
  formatting churn — were reverted to byte-for-byte their pre-F16 form.
- `OutfitsCubit`'s `repository` parameter now defaults to a fresh
  `InMemoryOutfitsRepository()` and is **named**, not positional (Dart
  disallows mixing optional-positional with named parameters in one
  signature, and `clock` had to stay named for existing call sites to
  need no edit) — implemented via a forwarding `factory` constructor so
  the default is resolved exactly once (not once per internal use).
  `lib/app.dart` and `outfits_cubit_dual_mode_test.dart`'s call sites were
  updated to pass `repository:` by name.
- The tautological `F16_A15` marker test was removed (A15's actual
  claim — "the full pre-existing suite passes unmodified" — now holds
  structurally, since `outfits_cubit_test.dart` is unmodified).
- `FirestoreOutfitsRepository.watchOutfits()` now sorts newest-first by
  `id` descending (previously Firestore's native lexicographic-by-doc-id
  order), matching guest mode's always-newest-first ordering — a
  user-visible mode difference the original implementation missed.
- Controller ruling implemented: `logWear`/`removeWear` now roll the
  Cubit's own optimistic `worn`/`wearLog` change back to its pre-call
  value on a repository transaction failure (D6 "reconcile on failure" —
  a transaction never queues offline, so a failed one has no later
  snapshot to reconcile from). The `_logError` label on the repository
  write's own catch block was also corrected (`'logWear failed'` →
  `'logWear repository write failed'`) and the chained
  `WardrobeCubit.adjustWears` call now has its own separate try/catch
  with its own distinct label, so a failure there is never misattributed
  to the repository write.

## Issues discovered
- **F16-A21's literal "two genuinely concurrent calls" shape is not
  reliably testable against `fake_cloud_firestore`.** A `Future.wait([...])`
  pair of real concurrent `logWear` calls against the same outfit was tried
  first; it lost an update (`worn` landed on 1, not 2) because
  `fake_cloud_firestore` has no optimistic-concurrency/retry-on-conflict
  model of real Firestore — both transaction bodies read `worn: 0` before
  either commits. This is the exact same fake-double limitation F15
  documented for `WardrobeRepository.adjustWears` ("such a test
  flakes/fails against the fake double regardless of the production code's
  correctness"). Resolved the same way F15 did: A21's test instead runs the
  two calls sequentially with a deliberately-stale shared `outfit` argument
  (proving the increment comes from a fresh server read, not the cached
  argument) plus a second structural test cross-referencing A09's
  `runTransaction` check. Documented inline in the test file; flagging here
  too since it's a recurring fake-double limitation worth a future task
  knowing about before attempting a "real" concurrency test against this
  package.
- **Async-ification of `OutfitsCubit.logWear`/`.removeWear` broke three
  pre-existing tests that assumed the `WardrobeCubit.adjustWears`
  cross-feature call lands synchronously inline with the triggering call.**
  Fixed by inserting microtask-flush points (`await
  Future<void>.delayed(Duration.zero)` / `await tester.pump(Duration.zero)`)
  at the specific points where each test's *baseline* or *final* assertion
  depends on that call having landed — never by changing what is asserted.
  This is a direct, deliberate consequence of F16-A18/A19's binding
  requirement that the wardrobe call happen *after* the repository Future
  resolves, not before — the two requirements (F16-A18/A19's ordering vs.
  "zero existing assertion edited") are only reconcilable by adjusting
  *when* a pre-existing test checks, not *what* it checks. Called out
  explicitly per the implementer contract's "if your changes would alter
  an existing test's assertions, stop and report" line: no assertion's
  *content* changed, only the moment it runs, and it was necessary rather
  than optional given A18/A19 are binding, named assertions in the feature
  doc this task is required to satisfy.
- `docs/features/F16-saved-outfits-backend.md`'s claim ("No
  `docs/foundation/*.md` changes expected... confirm this holds") was
  confirmed — no foundation doc changes were needed.
