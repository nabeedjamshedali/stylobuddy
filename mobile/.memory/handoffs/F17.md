# Handoff — F17 Calendar / Planner Backend

## Completed
- `lib/features/calendar/repository/planner_repository.dart`: abstract
  `PlannerRepository` interface (`watchPlanned()`, `plan(key, entry)`,
  `remove(key)`). `select`/`selectDate`/`navigate`/`startScheduling`/
  `clearEditing`/`label`/`keyFor` deliberately stay off the interface
  (transient-state, per schema doc §7).
- `lib/features/calendar/repository/in_memory_planner_repository.dart`:
  guest-mode repository, today's `SeedData.planned` moved behind the
  interface verbatim. `plan`/`remove` return `SynchronousFuture` (not
  `async`); a synchronous `snapshot` getter backs `PlannerCubit`'s
  first-frame seed. No Firestore/http/supabase import.
- `lib/features/calendar/repository/firestore_planner_repository.dart`:
  signed-in repository under `users/{uid}/plannedEntries/{dateKey}` — the
  Firestore doc ID *is* the `'yyyy-MM-dd'` key, no `id`/`date` field ever
  written (the one collection that departs from the duplicate-id
  convention, per the doc). `plan`/`remove` are plain `set()`/`delete()`,
  no `runTransaction` (neither is read-modify-write).
- `lib/features/calendar/cubit/planner_cubit.dart`: rewritten to take an
  optional named `repository` parameter via a factory (defaults to a
  freshly-resolved `InMemoryPlannerRepository()`, resolved once). Public
  method names/signatures unchanged. `plan`/`remove` now:
  optimistically update `state.planned` synchronously, fire the
  repository call as an unawaited async block with try/catch, log on
  failure, and roll `state.planned` back to the pre-call value on
  failure. Constructor subscribes to `watchPlanned()` with an `onError`
  handler; `close()` cancels that subscription.
- `lib/app.dart`: `PlannerCubit`'s `BlocProvider` now constructs
  `InMemoryPlannerRepository()` for `uid == null` and
  `FirestorePlannerRepository(FirestoreService(firestore:
  widget.firestoreOverride), uid)` for a signed-in uid, mirroring the
  Tasks 2/3 pattern exactly.

## Issues discovered
- None outside this feature's scope. The brief's "settled, non-negotiable"
  list (SynchronousFuture, optional named repository param, no
  transaction, no `id` field, catchError on every fire-and-forget write,
  onError on the stream, rollback-on-failure, real app.dart-level
  dual-mode test) was followed from the first implementation pass — no
  fix round was needed.
- F17-A06 and F17-A18's tests use the same style already established by
  F16-A09 (`firestore_outfits_repository_test.dart`): a source-string
  check (for A06, asserting the *absence* of `runTransaction` in
  `plan`'s body) and a fail-on-call repository double (for A18). Flagging
  this explicitly in case a reviewer expects a different mechanism for
  the "negative" (absence) case than F16's "positive" (presence) case —
  the source-string approach is symmetric with that precedent.

  such unawaited call exists..."); not needed here — both `plan` and
  `remove` are genuinely fire-and-forget at their own call sites, so the
  test (`F17_A15`) exercises the catch-and-log path non-vacuously.
